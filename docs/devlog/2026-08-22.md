## 막힌 것 / 해결

### Q1. TransferHistory 필드에서 account는 FK로? String으로?
→ **자기 계좌는 FK(@ManyToOne), 상대방 계좌는 String**
- 이 테이블의 존재 이유가 "내 통장 조회 최적화" → 자기 계좌는 FK 걸어야 조인·인덱스 최강
- 상대방 계좌는 타행 이체면 우리 DB에 없어서 FK 못 검
- Transaction 테이블(시스템 로그)에서는 둘 다 String으로 뒀던 것과 다른 이유 이해

### Q2. Transaction과의 관계는?
→ **@ManyToOne(fetch = LAZY) + @JoinColumn(name = "transaction_id", nullable = false)**
- 원본 이체 기록 참조 필수 (감사·재처리 시)

### Q3. balanceAfter가 있는데 잔액 관리 테이블(Account)이랑 어떻게 다른가?
→ **역할이 다름. 둘 다 필요.**
- Account.balance = 현재 최신 잔액 (실시간 갱신)
- TransferHistory.balanceAfter = 그 이체 직후 잔액 스냅샷 (통장 조회 즉시 표시용)
- 서비스에서: withdraw() 후 → history.balanceAfter = account.getBalance() (스냅샷)

### Q4. 프로그래머스 "다리를 지나는 트럭" (Level 2, 큐 시뮬레이션) 못 풂
- 접근 자체 잘못. 대기 트럭 큐만 만들고 다리 큐를 못 만듦
- "정적 계산(합/나누기)으로 되지 않을까"라는 오해 → 반례로 부정
- 다리를 큐로 모델링해야 하는 개념 처음 배움 (공간을 시간으로 흐르게 하려면 큐)
- 오늘은 통과 못 하고 재도전 리스트로 (2~3일 후 재시도)

### 추가로 배운 것
- **Double-entry(복식부기)**: 이체 1건 = TransferHistory 2건 (송금/수신 관점)
- **큐 시뮬레이션 개념**: 앞(front) = 곧 나갈 것, 뒤(back) = 방금 들어온 것. poll = 시간 흐름, offer = 새 이벤트
