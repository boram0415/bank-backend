## 막힌 것 / 해결

### Q1. `@NoArgsConstructor(access = PROTECTED)` — protected가 JPA한테 효과 있는 건가, 아니면 외부 생성 막는 용도?
→ **둘 다 맞고, 핵심은 후자.**
- JPA는 리플렉션으로 객체를 만들기 때문에 protected여도 문제 없이 씀
- 개발자가 실수로 `new Transaction()` 빈 객체를 만들면 도메인 무결성이 깨짐
- protected로 잠가서 JPA는 통과, 외부는 차단하는 게 목적

### Q2. Transaction과 Account 테이블 조인해야 하나? 그냥 이력 테이블이니까 String으로 둬도 되나? 인덱스만 걸면 되나?
→ **String으로 두는 게 실제 은행/금융권 관점에서 더 정석.** 이유 3가지:
1. 계좌 삭제/변경돼도 이력은 남아야 함 (FK 걸면 삭제 시 꼬임)
2. 타행 이체는 우리 DB에 그 계좌가 없어서 FK 못 검
3. 감사(audit)용 이력은 "당시의 계좌번호"를 그대로 보존하는 게 원칙
- 대신 fromAccount, toAccount 컬럼에 **인덱스 필수** (`@Table(indexes = ...)`)
- 조회 성능은 조인 없이 인덱스만으로 충분

### Q3. status는 나중에 수동으로 update? 코드에서?
→ **정답. 도메인 메서드로 수동 변경.**
- Setter 없이 `markSuccess()`, `markFailed(reason)` 도메인 메서드로만 상태 바꿈
- 서비스 로직에서 try/catch로 성공/실패 분기 후 호출
- 이 방식이 "정합성 설명 가능"의 실체 — 면접 무기

### 추가로 배운 것
- `@ManyToOne` 기본이 EAGER → 반드시 `fetch = LAZY` 명시 (N+1 방지)
- `@Enumerated(EnumType.ORDINAL)` 절대 X → 순서 바뀌면 데이터 오염
- 돈은 무조건 `BigDecimal` + `precision/scale` (`Long`/`double` 금지)
- IntelliJ가 `org.springframework.transaction.TransactionStatus`를 자동 import하는 함정 (Transaction 이름 때문). 그래서 `TranStatus`로 이름 지은 게 결과적으로 좋은 선택
